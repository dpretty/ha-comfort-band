# Comfort Band

Per-room HVAC band-control for Home Assistant. Heats below a low threshold, cools above a high threshold, idles in between — giving heat pumps and mini-splits margin instead of fighting to hold a single setpoint.

**v0.16.0** makes losing a room sensor visible. A zone whose temperature sensor goes unavailable can't control at all, and that used to be completely silent — found live: a master bedroom that drifted several degrees below its band for hours after its Thread sensor left the mesh, with nothing in the UI to say so. A new `binary_sensor.{zone}_room_sensor_unavailable` (device class `problem`) plus a rate-limited warning naming the sensor make it alertable; pair the sensor with a `for:` of a few minutes to ride out blips. A non-finite reading (`nan` or `±inf`) now counts as no reading, since `nan` parses as a float but compares false against everything — leaving hysteresis latched on whatever it was already doing, with nothing alerting. Scope note: this reports the failure, it doesn't change what the zone does about it — a zone that goes blind mid-cycle keeps running what was last commanded, as before.

**v0.15.0** fixes an MPC failure mode where a zone could idle while sitting several degrees below its band. When a slow-to-heat room only gets brief heat blips, the learned "heating slope" can be estimated *negative* (the model thinks heating cools the room), so MPC picks idle instead of heating. A new sign guard discards any recovery slope with a physically-impossible sign (heating can't cool; cooling can't warm) — `recovery_slope_heat`/`_cool` become `None` (`method_* = "rejected"`) and the zone falls back to heating/cooling toward band. Idle drift keeps both signs. MPC zones that previously trusted a wrong-sign slope now move toward band instead of idling; zones with clean data are unaffected.

**v0.14.1** hardens v0.14.0: a profile rename, delete, or clone now keeps the per-profile slots inside shared schedules in sync too (so an assigned room keeps following the shared band instead of silently dropping to its manual band), and the transition-time validator now rejects impossible hours like `24:00` cleanly instead of letting them raise a raw error mid-parse.

**v0.14.0** adds **named shared schedules** — let open-door rooms target one band over the day instead of fighting. Create a named schedule (e.g. *Bedrooms*) with `comfort_band.create_shared_schedule`, then point each room at it with the new per-zone `select.{zone}_schedule_assignment` (default *Own schedule*). Assigned rooms resolve their bands from the shared schedule live: edit it once (`comfort_band.set_schedule` with `shared_id`, or the card's schedule editor) and every member follows — so two bedrooms with an open door stop heating one while cooling the other. Shared schedules stay profile-aware (home/away still differ), feed MPC pre-heat and the band-ramp the same as own schedules, and per-zone overrides still win. It's an additive overlay: each room keeps its own schedule intact and reverts to it losslessly on unassign, so there's no migration and no behaviour change until you assign a room. Services to `create` / `rename` / `delete_shared_schedule` (delete refuses while rooms are assigned unless you pass `cascade: true`) and `assign_schedule` round it out.

**v0.13.0** adds opt-in **deterministic fan-boost**. Comfort Band can now command the climate's fan mode by action: a configured **active** fan while heating/cooling (faster recovery), and a quieter **idle** fan while the unit is air-cycling in `fan_only`. A new `switch.{zone}_fan_control_enabled` (default OFF) turns it on; two `select.{zone}_active_fan_mode` / `_idle_fan_mode` pickers list the unit's own `fan_modes`, so you choose from exactly what the hardware supports. This fixes the reported gym annoyance — a manually-raised fan stuck on full speed even after the room reaches band and the unit drops to fan-only. Modes are stored as strings (robust to a unit re-ordering them), skipped when unset (set only the idle side if you like) or already current (no redundant commands), and left alone on a climate with no fan support. Only the fan attribute is touched, which the learning buffer ignores, so this can't disturb MPC. No behaviour change for existing zones until you enable it.

**v0.12.0** keeps MPC ready through a morning heating chase. The idle (passive heat-loss) slope is a slow-changing thermal property, so the integration now remembers the last good one beyond the 90-min sample window. When a heating-dominated room (e.g. a gym chasing a rising morning band) yields only short idle blips and the live `idle_slope` goes `None`, the remembered value is substituted so `binary_sensor.{zone}_mpc_ready` stays on and anticipatory pre-heat keeps working — instead of MPC falling back to the reactive predictor exactly when pre-heat is needed. Persisted across restarts; expires after 24 h and is cleared on a manual edit or sensor swap so a stale thermal model can't mislead MPC. `sensor.{zone}_thermal_slope` gains `idle_slope_source` (`live` / `cached` / `none`) and `idle_slope_cached_age_min` so you can see when MPC is running on the cached value. The cache is scoped to MPC — the reactive hysteresis and the v0.7 predictor always run on the live slopes, so reactive/predictive control is unchanged and a cached idle can never silently suppress a heat/cool call.

**v0.11.0** adds comfort feedback — the foundation for the v3 auto-learning loop. A new `comfort_band.record_feedback(zone, label)` service logs how the current band feels (`too_hot` / `just_right` / `too_cold`), enriching each entry with the live room temperature, effective band, and action. Entries persist in a separate, capped `comfort_band.feedback` store (kept out of the main config); a `comfort_band/get_feedback(zone, since?)` websocket command reads them back. The companion card surfaces three pills on the Now tab. No behaviour change for existing zones — this is pure data capture for a later "you keep marking 22:00 as too warm — lower the band?" nudge.

**v0.10.1** stops autonomous HVAC fan-speed changes from flushing the learning buffer. The manual-edit detector compared `fan_mode`, so an HVAC that varies its own fan speed (or reports a different fan_mode in `fan_only` idle vs `heat`/`cool`) wiped the sample buffer on every idle↔active transition. The buffer then never held idle *and* recovery samples at once, so `binary_sensor.{zone}_mpc_ready` never turned on and MPC silently fell back to the reactive predictor — no schedule-lookahead pre-heat. The detector now compares only `hvac_mode` + `target_temp` (still catching genuine manual setpoint/mode edits, including physical-remote ones); `fan_mode` is still captured per-sample.

**v0.10.0** adds band-ramp smoothing: set `number.{zone}_band_ramp_minutes` to a non-zero value (e.g. 30) and schedule transitions interpolate linearly within ±ramp/2 of each transition. A 4 °C overnight rise at 06:00 becomes a 30-min shoulder instead of a wall — gentler HVAC, less overshoot. Per-zone, opt-in (default 0 = stepped, the v0.9.x behaviour). MPC's lookahead sees the ramp too.

**v0.9.2** makes the room-temperature sensor swappable post-add via the existing zone OptionsFlow. Swapping flushes the zone's sample buffer so the slope estimator restarts cleanly; schedules and learning state are preserved. Pairs with v0.9.1's diagnostics: if `std_dev_idle` sits near 0, your sensor is too coarse — this OptionsFlow lets you swap to a finer one in one click.

**v0.9.1** adds per-segment diagnostics to `sensor.{zone}_thermal_slope` — `sample_count_*`, `std_dev_*` and `method_*` attributes let users spot when a slope estimate is unreliable due to a low-resolution sensor sitting on the same quantized value for hours. The slope reports 0 in that regime not because the room is stable but because the sensor can't see the drift. No behaviour change.

**v0.9.0** teaches the v0.8 MPC to see upcoming schedule transitions. The coordinator computes the per-minute `(low, high)` band the schedule resolves to over `mpc_horizon_minutes`, and the cost function scores each candidate action against the band that will be active at end-of-horizon (not the band frozen at the snapshot). A morning band-rise from `(16, 19)` → `(20, 22)` at 07:00 now triggers pre-heat well before 07:00 instead of being chased reactively. Same release adds an **idle-preference tie-break**: when `idle` achieves full-horizon in-band coverage, it wins over heat / cool even if a recovery action lands closer to band midpoint — stops MPC burning compressor cycles on margin gains the room already has. Default `mpc_horizon_minutes` bumped 20 → 60; existing zones keep their explicit value (bump manually toward 60 to unlock the full pre-heat window). **Behaviour change for existing `mpc_enabled` users:** steady-state operation will see fewer heat/cool cycles than v0.8.1 because idle-preference now wins ties.

**v0.8.1** relaxes the v0.8.0 MPC cold-start gate so heat-only and cool-only zones activate MPC after the first idle + matching-recovery segment accumulates (was: required all three). Per-refresh safety bail-out defers to the v0.7 predictor when the room genuinely needs the missing direction. No behaviour change for fully-equipped zones.

**v0.8.0** adds a model-predictive controller as the third decision layer in the stack. Each refresh, MPC enumerates a small action space (`idle`, `heat → band's high edge`, `cool → band's low edge`), simulates each forward over `mpc_horizon_minutes` (default 20 min) using the v0.6 thermal slopes, and picks the action that maximises projected time-in-band. Behind a new opt-in `switch.{zone}_mpc_enabled` (default OFF) layered on top of `learning_enabled`; cold-start gated by `binary_sensor.{zone}_mpc_ready` (True once enough samples in idle / heat / cool segments have accumulated). v0.7's predictor remains the fallback during warm-up. v0.8 also captures the climate's `fan_mode` attribute in each sample (recorded but unused — v0.9 will partition slopes by `(action, fan_mode)` and grow MPC's action space to include fan-mode candidates). Builds on the v0.1 core (per-zone entities, asymmetric-deadband hysteresis, profile-driven schedules), v0.2 schedule WS subscription, v0.3 profile CRUD, v0.4 apparent-temperature support, v0.5 cross-mode min-cycle dwell, v0.6 learned thermal-slope estimator, and v0.7 passive drift acceptance.

The Lovelace card lives in a separate repo — install [dpretty/ha-comfort-band-card](https://github.com/dpretty/ha-comfort-band-card) via HACS as a Dashboard Custom Repository.

Defaults to **shadow mode** per zone (`switch.{zone}_enabled = off`) so you can verify decisions side-by-side with your existing setup before cutting over.
